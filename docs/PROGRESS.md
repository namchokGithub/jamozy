## Current Focus

**MVP status:** The core Learning Path, Lesson Result, Review, Guest-local persistence, authenticated Firebase persistence, settings, profile flows, and single-owner Admin BO are complete. The Admin BO production rollout deployed indexes and Rules, migrated 5 legacy content documents, verified the owner claim with a successful content edit, and has Firestore Rules Emulator coverage. The remaining tracked work is post-MVP UX, deployment automation, and the planned Learning Modes.

**Light-theme UI:** All learner-facing routes now share Home's warm cream, pastel, rounded visual language through presentation-only components in `src/components/ui/`. Course Map, Lesson, Review, Profile, Settings, Auth, typing keyboard, and recovery pages are covered. Shared `Modal`, native-select `Dropdown`, and `SnackbarProvider` are UI-only; dark theme and animation remain deliberately deferred.

**Deferred architecture:** [[DEC-022]]–[[DEC-029]] define future vocabulary, shared learner-state checkpoints, Learning Modes, and richer session-history consumers. `VocabularyProgress`, `JamoStats`, Topic/Position practice, Daily Quest, and History UI are not missing MVP scaffolding; they remain explicitly deferred.

**Implementation detail:** Keyboard settings and Review preview context ship through the active learner repositories. `showKeyboard`, `showEnglishKeys`, and `keyboardOpacity` flow from route-loaded `UserSettings` into both `LessonTypingSession` and `ReviewTypingSession`, then into `VirtualKeyboard`; new profiles default to `keyboardOpacity: 0.7`, while saved settings are unchanged. `showEnglishKeys` is removed from the target model by [[DEC-027]]. `ReviewPage.loader.ts` loads due items and settings in parallel, then calls `application/get-review-previews.ts`, which batches unique source-lesson reads and joins each item to an optional exercise. The Review preview applies the existing meaning/romanization preferences and retains Korean-only rows if a source lesson or exercise no longer exists. Sound, dark mode, and vocabulary metadata remain outside active typing sessions. Verification results are recorded in `docs/COMPLETE-LOG.md`.

A read-only `/profile` page ships end to end: `application/get-profile-summary.ts` (mirrors `get-settings.ts`'s pattern — pure read, falls back to `defaultUserProfile` for a new user, never writes) feeds `ProfilePage.loader.ts` → `ProfilePage.tsx`, showing level, an EXP progress bar (`exp % 100` out of the existing flat-100-per-level rule), and all 6 `UserStats` fields. `ProfilePage.loader.ts` derives Lessons completed from persisted `LessonProgress` records marked `completed`, so it matches Course Map and does not change merely because content adds Units or Lessons. Its session-foundation compatibility mapping adds raw session exercises, best accuracy, and typing time to a zero-valued baseline; it derives accuracy/WPM from accepted/rejected keystrokes and duration when no legacy aggregate exists. A non-zero legacy baseline retains its stored averages because their denominators cannot be reconstructed. A new pure `format-typing-time.ts` formats `totalTypingTimeSeconds` (its own file, same Fast-Refresh-avoidance reason as `format-exercise-meaning.ts` below). Followed the full architectural path: spec (`docs/superpowers/specs/2026-09-24-profile-dashboard-design.md`) → plan (`docs/superpowers/plans/2026-09-24-profile-dashboard.md`, 5 tasks) → native execution → fresh Opus review. Reviewer found 0 Critical, 3 Important (fixed 2: `averageAccuracy`/`bestAccuracy`/`averageSpeedWpm` were rendering as long unrounded floats for any real user since they're running averages, now `Math.round`ed for display only — stored values untouched; the spec's EXP progress bar was text-only, now a real `<progress>` element — 3rd Important was this doc-upkeep pass itself, done here), 3 Minor deferred (see below). 189/189 tests, clean tsc/lint. Live-verified: existing-user rendering against real Firestore data in the user's own Chrome (Level 3, partial EXP, unscaled accuracy — this is what surfaced the rounding issue the reviewer then caught precisely), and the true zero-state in a separate, isolated Playwright browser (Level 1, all stats zeroed, no NaN/undefined) after a manual-testing storage-clearing step left the user's own Chrome profile's `localhost:5173` IndexedDB stuck (self-inflicted test-process issue, not an app defect — the user was given a one-line fix: close other `localhost:5173` tabs or clear site data for `localhost`).

`meaningLanguage` and `romanizationEnabled` were first wired into `LessonDetailPage`'s exercise list. `LessonDetailPage.loader.ts` fetches `getLesson`/`getSettings` in parallel via `Promise.all` (they don't depend on each other) and passes `settings` through. Rendering is gated by a pure `format-exercise-meaning.ts` (`formatExerciseMeaning(exercise, meaningLanguage)`, th/en/both, omits an empty meaning field rather than rendering a blank slot, returns `null` when nothing to show) — extracted to its own file after exporting it from the component file broke Vite Fast Refresh (`react-refresh/only-export-components`). The latest keyboard/Review round extends these same preferences to Review preview; see the opening paragraph above.

The Settings UI itself shipped end to end in the prior round (see [[DEC-020]]): `/settings` (`SettingsPage.tsx`) reads/writes `UserProfile.settings` via `get-settings.ts`/`update-settings.ts`. This round completes the keyboard visibility/English-label/opacity consumers and the Review-preview meaning/romanization consumer; only sound and theme remain persist-only. `defaultUserProfile` moved from a private helper in `complete-lesson.ts` to an exported `domain/models/user-profile.ts` function, reused by both, with `complete-lesson.test.ts` left unmodified as the regression proof.

Manual browser verification against live Firestore caught two real, independent bugs neither unit tests nor the fetcher-state fix alone caught — see [[DEC-020]] for the full narrative: (1) `useFetcher().state` passes through `submitting → loading → idle` after a successful action (the route's own loader revalidates), not just `submitting → idle` — a first fix tracking only "was submitting" missed the `loading` phase; (2) the "has this changed since the last save" check used `JSON.stringify(a) === JSON.stringify(b)`, which breaks when two structurally-identical objects have their keys in a different insertion order — exactly what happens between a Firestore-sourced object and a Zod-`.parse()`-returned one. Both are fixed, both have regression tests confirmed RED against the old code and GREEN against the fix, and a fresh whole-branch review independently reproduced both fixes' correctness by reverting each and confirming its own test fails.

A fresh whole-branch review (Opus) found no Critical issues. The one Important finding was this documentation-upkeep pass itself, done here. 7 Minor findings deferred, not fixed this round (see below).

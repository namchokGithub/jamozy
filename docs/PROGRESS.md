## Current Focus

The Settings UI now ships end to end (see [[DEC-020]]): `/settings` (`SettingsPage.tsx`) reads/writes `UserProfile.settings` via `get-settings.ts`/`update-settings.ts`, a persist-only form this round — none of the 7 settings (sound, keyboard visibility/opacity, romanization, meaning language, theme) actually change any other screen's behavior yet, deliberately deferred to a future round, one setting (or cluster) at a time. `defaultUserProfile` moved from a private helper in `complete-lesson.ts` to an exported `domain/models/user-profile.ts` function, reused by both, with `complete-lesson.test.ts` left unmodified as the regression proof.

Manual browser verification against live Firestore caught two real, independent bugs neither unit tests nor the fetcher-state fix alone caught — see [[DEC-020]] for the full narrative: (1) `useFetcher().state` passes through `submitting → loading → idle` after a successful action (the route's own loader revalidates), not just `submitting → idle` — a first fix tracking only "was submitting" missed the `loading` phase; (2) the "has this changed since the last save" check used `JSON.stringify(a) === JSON.stringify(b)`, which breaks when two structurally-identical objects have their keys in a different insertion order — exactly what happens between a Firestore-sourced object and a Zod-`.parse()`-returned one. Both are fixed, both have regression tests confirmed RED against the old code and GREEN against the fix, and a fresh whole-branch review independently reproduced both fixes' correctness by reverting each and confirming its own test fails.

A fresh whole-branch review (Opus) found no Critical issues. The one Important finding was this documentation-upkeep pass itself, done here. 7 Minor findings deferred, not fixed this round (see below).

**Still open, not forgotten:** [[DEC-015]]'s MVP-only security gap. [[DEC-018]]'s `ReviewItem.id` uniqueness constraint (still documented, not enforced). [[DEC-019]]'s review-system Minor findings (still deferred, unchanged this round). New from this round's review, all deferred as genuine Minors: Save re-enables during the post-save loader revalidation (not just `submitting`, so it's briefly clickable while Firestore's confirmation read is still in flight — the write itself is idempotent, so the cost is at most one redundant write); "Saved" can show a moment early when nothing was actually edited before clicking Save; `getSettings` doesn't merge stored settings over `defaultUserProfile`'s defaults field-by-field, so a hypothetical future document missing a field (or a future 8th setting added to the schema) would leave that one input `undefined` and make Save fail Zod validation instead of degrading gracefully; a Save failure replaces the whole page via `RouteError` rather than an inline error, losing unsaved edits (matches every other route's existing behavior, not new); no Firestore transaction around the settings read-modify-write, so a settings save and a lesson completion in two tabs at the exact same moment could theoretically lose one update (matches `complete-lesson`'s existing pattern); the multi-phase fetcher-state regression test doesn't itself assert the Save button was disabled during the `submitting` phase (a fresh reviewer independently confirmed via a render probe that the phase happens and the test does catch the bug, just not self-documenting that specific assertion); "Saved" has no `aria-live`/`role="status"` for screen readers, and the opacity slider doesn't display its current numeric value.

`pnpm build`/`lint`/`vitest run` all pass (163 tests).

Next real steps, not blocked on each other: (1) wire individual settings into their consumers, starting with whichever the user wants first (meaning-language filtering and romanization toggle are the cheapest, since the exercise data already has both fields — sound and real dark-mode CSS are bigger, cross-cutting changes), (2) a dedicated dashboard/profile page surfacing EXP and level persistently, (3) a proper Lesson Result screen (currently just an inline block), (4) revisit [[DEC-015]]'s security gap before any real launch.
